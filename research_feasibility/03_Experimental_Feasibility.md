# 03 实验可行性：模型、服务器与访问边界

**现状：** 实验室“约 30B Qwen”只是一条未经核实的口头信息；目前未知模型 ID、是否有 API、能否读取权重、硬件和配额。以下是条件分析，**没有连接服务器、下载权重或运行模型**。模型规格取自 [Qwen3-30B-A3B 卡](https://huggingface.co/Qwen/Qwen3-30B-A3B)、[Qwen3-Coder-30B-A3B-Instruct 卡](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct)、[Qwen3-32B 卡](https://huggingface.co/Qwen/Qwen3-32B) 与 [Qwen 文档](https://qwen.readthedocs.io/en/latest/framework/function_call.html)。

## 候选模型的实际差别

| 可能部署的模型 | 架构／模式 | 对 L1 Coding Agent 的适配性 | 对 L3 的特殊问题 |
|---|---|---|---|
| Qwen3-Coder-30B-A3B-Instruct | 约 30.5B 总参数、约 3.3B 激活的 MoE；官方卡给出 48 层、128 专家中每 token 激活 8 个，原生长上下文；**仅非 thinking 模式** | 首选候选：针对 agentic coding 和工具调用调优；须实测所部署版本是否正确解析函数调用、能完成我们的任务 | 专家路由、量化和不同实现使激活对齐与 patching 更复杂；不应期待可见 `<think>` 内容 |
| Qwen3-30B-A3B | 同量级 MoE；原始卡支持 thinking／non-thinking 两种模式 | 可做通用能力对照；两模式不能混在同一主比较中；官方卡注明 32,768 原生、可用 YaRN 扩展 | 内部分析同样受 MoE 路由影响，思考模式增加对齐困难 |
| Qwen3-32B | 32B 稠密模型；原始卡为 64 层，支持工具调用 | 如果部署的是它，可用于 L1；编码性能须先摸底，不能按 Coder 版本推断 | 稠密架构较利于固定层激活比较，但总权重和显存更高 |
| 其他 30B／32B、量化或微调版 | 未知 | 先确认具体 checkpoint、chat template、工具 parser 和是否被额外系统提示包装 | 基座差异、微调和量化可能改变方向；先在原部署环境复现行为 |

Qwen 官方分别推荐 [vLLM／SGLang 服务](https://qwenlm.github.io/blog/qwen3/)；模型卡给出各自的模板与加载示例。**模型的工具调用能力不等于服务器 API 已启用对应 parser**，必须做三步烟测：函数调用能被正确解析、工具结果能回填、多轮执行能够停止。

## 黑盒、灰盒与白盒能力矩阵

| 可用权限 | 能做什么 | 不能可靠声称什么 |
|---|---|---|
| 仅 OpenAI 兼容 API | L1 全部：固定 Harness、随机分组、日志、任务成功、调用序列和成本；L2 的同会话／摘要／新会话对照 | 读不到隐藏层；不能直接做目标模型的 activation steering／patching；某些 API 不保证 seed 完全可重复 |
| API + 服务端扩展／hook | 可记录指定层激活、专家路由、logprobs（取决于实现），可能做在线干预 | 扩展是否可用取决于管理员和部署版本；不能把自定义服务接口当标准 OpenAI API |
| checkpoint + 独占 GPU + 模型代码 | 可用 Transformers 提取隐藏态、hook 残差流、训练 probe、steering／patching；也可自己部署 vLLM／SGLang | 仍需处理量化差异、MoE 路由和内存；能加载权重不自动意味着能在原生产服务上干预 |

[vLLM 隐藏态提取文档](https://docs.vllm.ai/en/latest/features/speculative_decoding/extract_hidden_states/)已有离线提取特性，但主要面向 EAGLE 等场景，**不应等同于任意层、任意 token、在线 steering 均开箱可用**。L3 首选可读权重的 Transformers／PyTorch hook 做小批量受控分析，性能不足时再考虑服务框架定制。SGLang 和 vLLM 适合 L1 吞吐，选择以实验室现有稳定部署为先；更换推理后端会改变解析、采样和批调度，应视为实验因素而非透明替换。

## 显存与算力的粗估（非采购承诺）

- BF16 仅权重：30.5B × 2 byte ≈ **61 GB**；32B × 2 byte ≈ **64 GB**。MoE 的 3.3B“激活参数”只意味着单 token 计算量较低，**并不意味着只需载入 3.3B 权重**。加上 KV cache、框架和批处理，单张 80GB 卡可能在短上下文、小批量下可用，但是否稳定必须实测；长上下文常需分卡或降并发。
- 4-bit 理想权重下界约 15–16 GB，实际还需量化元数据、非量化层、KV cache、runtime；显存和激活干预精度随量化方案变化。不能把“15GB”写成部署需求。
- L1 可用短代码库、限定上下文例如 8K–16K、每次执行 15–25 决策步来降低费用；最大上下文长度、输出 token 上限和超时须同条件固定。
- L3 即使只保存一个层的每 token 激活，也会占显著磁盘与 I/O；优先仅在预定义**决策位置**采集，不能全量保存推理长轨迹后再搜索“显著方向”。

## 需要实验室管理员确认的最小清单

1. **精确模型 ID／checkpoint hash**、基座还是 Instruct／Coder、是否有额外 LoRA 或系统提示、chat template 版本；是否支持 thinking 模式以及当前配置。
2. **部署栈**：vLLM、SGLang、Transformers 或其他，具体版本，函数调用 parser、reasoning parser、量化格式与精度（BF16／FP8／AWQ／GPTQ 等）。
3. **访问层级**：仅 API、服务器 shell、模型文件读取、可否起独立进程、可否安装依赖／加 hook；是否可导出激活或路由记录。
4. **硬件与配额**：GPU 型号、张数、每卡显存、当前共享负载、可用窗口、并发限制、token／请求配额、作业最长时长、磁盘配额。
5. **API 行为**：temperature/top_p/seed 是否可设、最大上下文与输出、工具调用 schema 支持、logprobs、timeout 和重试规则、服务端可能的隐藏记忆／压缩。
6. **安全边界**：允许的容器／隔离工作目录、是否可禁网络、写盘权限、日志保留与保密要求、故障时的恢复责任。

## 关键可行性风险与缓解

| 风险 | 对结果的影响 | 首轮验证方法 |
|---|---|---|
| 模型太弱或工具解析不稳 | 重复可能只是语法错误、规划循环 | 先做 12 个任务的无压力能力门槛；记录工具格式错误率 |
| 产品／实验室 Harness 强制测试 | 压力效应被固定规则覆盖，或现象只在产品中出现 | 固定透明最小 Harness；若有第二 Harness，做小样本交叉复核 |
| 服务端隐藏自动重试／上下文压缩 | 调用顺序与可见状态不真实 | 要求服务器返回原始调用 ID 和错误；本地 wrapper 给每次调用加 ID／状态版本 |
| GPU／配额不足 | 重复数不够，无法估计效应 | 先黑盒 L1；L3 在通过 L1 后单独申请资源 |
| MoE 路由和量化不稳定 | probe 可迁移性与干预解释弱 | 分层记录专家路由；同 checkpoint／精度下对照，报告跨部署失败 |
| 模型中没有现象 | 研究主假设落空 | 预注册停止／转向标准，保留负结果，不以事后换阈值制造“效应” |

## L2／L3 的进入条件

**L2：** 仅在 L1 有可重复、在成功率与调用成本上有意义的效应后进入。对每个新任务及相同工具状态，随机给四种上下文：①同会话保留完整失败历史；②同一历史的长度受控摘要；③只保留失败反馈及最后修复记录；④彻底新会话且没有历史。另设“外部持久记忆开启／关闭”专项对照，要求管理员确认服务端是否保存用户画像、长会话摘要、工具缓存或跨请求状态。四组还需一个长度相近的中性历史对照。

完整历史组有效，只能证明**同一上下文影响行动**；摘要或失败条目组有效，说明某些历史信息足以触发策略，而非凭空出现的记忆。全新会话组若无持久记忆和权重更新，**原则上没有可保留的内部跨会话状态**。若仍有差异，先排查外部记忆、服务器复用、任务分配和随机波动。即使 L2 成立，也不能单凭行为残留推断情绪机制。

**L3：** 需要可读取／干预权重及足够算力，并且 L1 效应稳健。建议按如下顺序，每步有停止门槛：

1. **Contrastive activation**：在相同任务、相同最终代码状态与相同可见证据下，配对压力／中性提示；于**行动前固定 token 位置**提取多层残差流，预先确定对比位置与层范围。保留工具输出和措辞版本，避免把失败词面本身当成隐藏概念。
2. **Linear probe**：训练集与测试集按**任务／仓库**划分，而非随机拆同任务的 token；再把高成本措辞改写或只改变计分数值，验证跨措辞迁移。比较仅用可见文本的 probe、状态／动作历史基线以及随机标签 probe。如果线性 probe 仅在同措辞里有效，不能称之为行为机制。
3. **Steering**：从训练任务求候选方向，在从未用于拟合的任务行动点加入或减去；测试零信息重复、必要验证、最终成功率、工具格式错误率与输出长度。随机方向、无关概念方向、反号、相同范数和 sham hook 都要做。把“总体少调用”与“只减少无效调用”分开。
4. **Patching／消融**：从配对无压力轨迹把目标层激活 patch 到有压力轨迹，反向亦然；同时检查 action logprob、实际工具动作和后续任务结果。必须说明 patch 的 token／层／幅度选择，并报告多种合理指标，因为方法细节可改变结论。[Zhang & Nanda](https://arxiv.org/abs/2309.16042)。

MoE 模型还需记录专家路由：若压力改变专家选择，直接 patch 残差流可能同时改变路由与语义；可先在相同路由子集或稠密 Qwen3-32B 上复核。量化版本的方向应与同 checkpoint 高精度版比对，不能假定同一向量在不同框架和精度下可移植。即使干预有效，也只能说**该激活组件对该行为有因果影响**；把它命名为“绝望”仍需独立语义和跨任务证据。[Anthropic 的方法与限制](https://arxiv.org/abs/2604.07729)、[agent 工具决策 probe](https://arxiv.org/abs/2605.06890)是最低比较基线。
