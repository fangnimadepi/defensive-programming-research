# 06｜计算资源预算

估算日期：2026-10-25。**下列为规划假设，不是实测吞吐、云厂商报价或本项目实验结果。**先按科学问题定义实验规模，再给配置。没有采用当前实验室设备约束。B 是推荐主路线；A/C/D 是可选择的扩展，不应默认全部相加执行。

## 1. 统一口径与公式

- GPU-hour 是卡数×运行小时，8 卡运行 10 小时为 80 GPU-hours，不是 10。
- episode 为一次独立 agent 任务；训练 rollout 为采样候选，两者计费语义不同。
- 输入 token 采用**每次调用计费输入的累计量**，包括重复上下文；不是最终 transcript 长度。
- 基准 episode：8 次模型决策，平均每次输入 4k/output 0.5k，累计输入 I=32k、输出 O=4k；峰值上下文约 8–16k。工具调用约 8 次，上限单独记录。
- 合成 Pilot 使用上述基准；真实代码任务可能平均上下文 16–64k、20–50 次工具调用。若累计输入/输出为基准 2–8 倍，应按实际 tokens 重新放大，不能沿用表格原数。

推理近似：

`H_infer = N × (O + α I) / (3600 q_gen) × f`。

α=.1 是输入处理相对解码的折算假设，敏感性范围 .03–.3；q_gen 是每张分配 GPU 的有效 token-equivalent/s，需包含张量并行卡数折算；f=1.5 计入调度/评估重试等开销。它不是模型 FLOPs 定律，长上下文和低并发下可能失效。

训练近似：`H_SFT = T_train / (3600 q_train) × f`。

RL：`rollouts = runs × updates × prompts_per_update × group_size`；`T_out = rollouts × mean_completion`；`T_train = rollouts × (prompt+completion) × reuse_epochs`；`H_RL = f/3600 × [(T_out+evaluation_equivalent_tokens)/q_gen + T_train/q_train]`。

RL 的 q_gen 采用包含 rollout prefill 的有效输出吞吐；不再另对训练 rollout 输入重复计入 α。下表 reuse_epochs=1。若算法重复利用轨迹多轮，T_train 相应增加。actor/reference/reward 的额外前向、padding、同步若未反映在 q_train 中，要另外计费。

**吞吐假设而非 benchmark**：小型开放模型推理 q_gen 30–150；Core 混合规模 15–80；Full 大模型 5–60。SFT 小型模型 q_train 100–800，Core 60–500，大型模型 20–200 tokens/s/GPU。RL Full 使用较收敛区间 q_gen 10–60、q_train 30–200。必须先实测 30–50 个代表 episode 和短训练循环，替换这些参数。

## 2. 参数规模与方法的显存差异

| 工作负载 | 权重与额外状态 | 最小合理配置示例 | 推荐配置及限制 |
|---|---|---|---|
| 7–14B 推理 | BF16 权重约 14–28GB，另加 KV/运行开销 | 1×48GB；7–8B 量化可尝试 24GB | 1–2×80GB，利于批处理；24GB 不是长上下文保证 |
| 30–35B 推理 | BF16 权重约 60–70GB | 1×80GB 小 batch，或 2×48GB | 2–4×80GB；长上下文预留 KV |
| 70B 推理 | BF16 权重约 140GB | 2×80GB 仅小 batch/短上下文；量化另论 | 4–8×80GB，避免权重能装下却无法采样 |
| 7–14B LoRA/QLoRA SFT | 底模冻结；优化器只作用 adapter，但激活不消失 | 1×48/80GB；QLoRA 可降低权重内存 | 2–4×80GB，checkpointing、packing；量化训练作为独立条件 |
| 32–70B LoRA | 权重、激活、adapter optimizer | 2–4×80GB，需分片；70B 偏向 4 卡以上 | 4–8×80GB，实测长序列与 batch |
| 全参数 Adam 类 SFT | 约 12–20 bytes/参数，另加激活与通信缓冲 | 8B 状态约 96–160GB；4×80GB 较合理 | 32B 约 384–640GB，通常 8–16×80GB；非 LoRA 等价预算 |
| RL | actor、reference、可能的 critic/RM、采样 KV、优化器 | 小模型 LoRA 可 2–4×80GB 分时运行 | 4–8×80GB 起；更大模型/异步 rollout 8–32 卡 |
| 激活干预 | 模型＋选择层激活＋hooks；通常不需训练梯度 | 7–14B 1×80GB | 2–8×80GB，流式保存；关闭梯度降低开销 |

80GB 卡可按 A100/H100 等实现，不能认为它们速度相同。48GB 可为 L40S 等；实际选择由吞吐测量决定。MoE 推理 FLOPs 与激活参数有关，但权重存储依赖**总参数**，不能把 235B/A22B 当 22B 显存需求。开放权重、稳定版本和可读取激活比特定品牌更重要。

## 3. Route B：激励与验证行为（推荐）

对应 [05](05_Experimental_Design.md) E1/E2，两个实验各占一半任务。

| 规模 | 实验量与数据 | 最小合理配置 | 推荐配置 | GPU-hours（全部自托管） | 存储与主要成本 |
|---|---|---|---|---:|---|
| Pilot | 20任务×8配置×2模型×3重复=960；30.72M input/3.84M output；约7,680工具调用 | 1×48GB，顺序跑两个7–14B模型 | 1–2×80GB；至少一模型家族外对照 | 20–100 | 50–100GB；主要为推理与日志审计 |
| Core | 60×12×3×5=10,800；345.6M/43.2M；约86,400工具调用 | 2×80GB 顺序跑7–35B | 4×80GB，三模型含独立家族 | 400–2,200 | 0.2–1TB；保留集、人工复核及长任务放大 |
| Full B | 120×16×5×8=76,800；2.4576B/307.2M；约614,400工具调用 | 4×80GB，可分时纳入70B | 8–16×80GB，多尺寸、多家族；真实代码迁移 | 4,000–47,000 | 1–3TB；上下文与工具等待是大不确定项 |

这些区间已含 f=1.5，未含更长上下文的 2–8 倍放大，也未保证某一统计效应的功效。上下文因素与吞吐区间相关，不能机械把每个最坏因素都独立相乘后当“可靠上界”。Core 三个模型应兼顾能力与可比性，而不是三个同源微调版本。

## 4. Route A：新增监督审计与暴露对照

三 SFT 臂：诚实/概念知识/策略示范。SFT tokens 是处理过的总量；例如 1M tokens 可来自约 1,000 条1k样本的一轮，5M/10M可相应增加数据或轮数，但重复数据必须单独记录。以有效 tokens/optimizer update=16k 预算，分别约 63/313/625 次更新，取整或尾批另记录。

| 规模 | 训练与评估运行数 | 最小合理配置 | 推荐配置 | 总 GPU-hours | 存储与成本依据 |
|---|---|---|---|---:|---|
| Pilot | 1尺寸×3臂×3训练种子=9run；1M/run，共9M SFT；9×20任务×3解码＋60底模=600episode | 1×48/80GB，7–8B LoRA | 2×80GB，训练/推理分时 | 20–100 | 0.2TB；训练约5–38h，另加推理/审计 |
| Core | 2尺寸×3×5=30run；5M/run，共150M；30×50×3＋300底模=4,800episode | 2×80GB，7–35B LoRA | 4–8×80GB | 310–2,100 | 0.5–2TB；训练约125–1,042h＋推理约180–960h |
| Full A | 3尺寸×3×5=45run；10M/run，共450M；45×100×5＋1,500底模=24,000episode | 4×80GB，最高70B LoRA | 8×80GB；量化条件单列 | 2,200–24,000 | 2–5TB；大模型训练约938–9,375h＋推理约1,200–14,400h |

数据审计比继续加种子更关键；9M/150M/450M tokens 不证明无知识暴露。对底模只保留一组对应评估，不把同一初始权重按训练种子当作独立模型。若改全参数 SFT，重新计算状态与吞吐，不能把此表直接套用。

## 5. Route C：训练动力学

三个奖励臂有漏洞代理/修补代理/真实目标；均从同一诚实起点分配。下表是**本项目候选小环境 RL**，不是任一生产研究的精确复现。

| 规模 | run、更新与采样 | Tokens 与评估 | 最小合理配置 | 推荐配置 | 总 GPU-hours |
|---|---|---|---|---|---:|
| Pilot | 1尺寸×3臂×3种子=9run；每run 100更新×16prompt×4候选=6,400rollout | 总57,600rollout；平均out1,024/总长2,048；58.98M生成、117.96M更新tokens；3检查点×20任务×3解码×9＋60底模=1,680eval | 2×80GB，7–8B LoRA，采样/更新串行 | 4–8×80GB | 300–1,500 |
| Core | 2尺寸×3×3=18run；300×16×4=19,200rollout/run | 总345,600；out2,048/总长4,096；707.79M生成、1.416B更新；6检查点×50×3×18＋300=16,500eval | 4×80GB，7–35B LoRA | 8–16×80GB，rollout 与学习分资源 | 5,500–33,000 |
| Full C | 3尺寸×3×5=45run；500×16×4=32,000rollout/run | 总1.44M；out2,048/总长4,096；2.949B生成、5.898B更新；6检查点×50×3×45＋450=40,950eval | 8×80GB，最高70B LoRA | 16–32×80GB；需调度与检查点管理 | 35,000–220,000 |

生成/更新 tokens 不是可相加后直接乘同一吞吐的工作量：生成串行解码较慢，更新反向传播也更贵；公式分别计。平均训练 prompt/完成长度仅为小环境设置，长 coding rollout 会显著放大。

数据需求：Pilot 约500–2,000独立训练任务、Core 5,000–10,000、Full 10,000–30,000，程序化生成并做机制去重；updates 中 prompt 可重采样，不能把57,600候选称为57,600独立任务。确认集不可进入在线奖励模型修补训练。

存储：Pilot 0.5–1TB，Core 2–5TB，Full 5–15TB，按保留 adapter、必要 optimizer 和选定轨迹估计。若保存每次全权重＋optimizer，空间会增至数十 TB：单70B BF16权重约140GB，45run×7份即约44TB，仅权重尚未含优化器。禁止无计划保存每个更新的完整状态。

外部校准：[L03 Appendix C](https://arxiv.org/html/2604.15149v1)报告每个对照 run 约64 H100×48h，即约3,072 GPU-hours；两个奖励臂约6,144。这证明小环境预算不等于生产或原论文精确复现。若 Pilot 必须做等规模复制，应采用该量级另立预算。

## 6. Route D：探针与激活因果干预

只在 B 已显示可重复行为后投入。干预配置计入零剂量、正负方向、随机方向、语义控制和恢复；不是全部选择最有利方向。

| 规模 | 运行与采集 | 最小合理配置 | 推荐配置 | GPU-hours | 建议存储 |
|---|---|---|---|---:|---|
| Pilot | 240采集＋10任务×8干预×2行为条件×3重复×1模型=720episode；probe ≥1,000决策状态 | 1×80GB，7–14B | 2×80GB，流式 hooks | 50–200 | 0.1–0.3TB |
| Core | 1,200采集＋30×12×2×3×2=5,520episode；probe ≥10,000状态 | 2×80GB，最高35B | 4–8×80GB | 600–2,500 | 0.5–2TB |
| Full D | 6,000采集＋60×16×2×5×3=34,800episode；probe ≥50,000状态 | 4×80GB，最高70B | 8–16×80GB | 5,000–42,000 | 2–10TB |

按相对 B 约2倍 hooks/干预开销估计，已合入总系数约3；D 单独采用 q_gen 为 Pilot 30–100、Core 15–60、Full 5–40，再为 probe 拟合和抽样回放留少量余量，得到表内取整区间。这里的2行为条件为验证与投机决策状态配对；具体抽样需避免只挑成功例。

激活体积：`bytes = 保存token位置数 × 层数 × hidden_dim × 每元素字节`。例如10,000决策位置×8层×4,096×BF16(2B)≈0.655GB；若保存100万token×32层×4,096，则≈262GB。对d=8,192，后者约524GB。全token、全层保存100M tokens可能超过50TB；推荐只保存决策位置、预选层、抽样完整轨迹，并在线计算低维特征。

probe 的小型拟合计算通常低于轨迹生成；稀有正例、标签质量、patching 对齐和重复剂量实验才是主要成本。开放模型的层数和 d 确定后必须重算，不能将隐藏维度示例当成所有模型规格。

## 7. API 对照成本

使用官方 [Claude API 定价页](https://claude.com/pricing)在本次调查时显示的两个标准价格档作锚点：Sonnet 4.6 输入 $3/百万、输出 $15/百万；Opus 4.8 输入 $5/百万、输出 $25/百万。价格不是模型选择建议；未假定缓存、Batch 折扣、税费、长上下文或工具服务附加费。

`USD = I_uncached/1e6 × p_in + O/1e6 × p_out + cache_write + cache_read + judge + tool + retry`。

基准32k/4k episode：$0.156–0.260。思考 tokens 如被计入输出，应包含在 O，不能漏记。

| B 规模 | 全部使用该价格档的对照估价 | 推荐仅一个 API 模型槽位 | 该槽位基础成本 | 加50% judge/重试预留 |
|---|---:|---:|---:|---:|
| Pilot | 960episode：$150–250 | 480episode、约3,840调用 | $75–125 | $112–187 |
| Core | 10,800：$1,685–2,808 | 3,600episode、约28,800调用 | $562–936 | $842–1,404 |
| Full B | 76,800：$11,981–19,968 | 15,360episode、约122,880调用 | $2,396–3,994 | $3,594–5,990 |

50%是规划预留：例如每episode两次8k输入/1k输出的裁判调用，约增加原生成成本50%；不代表真实标注方法必须采用两次模型裁判。人工真值核查仍必要。若同模型 API 作为替代槽位，该部分 GPU 预算扣除，不能同时把全部 GPU-hours 与全部 API 成本当必需开销。

A 的600/4,800/24,000评估 episode，若全部按同档 API 行为复核，基础约$94–156/$749–1,248/$3,744–6,240；实际训练后权重通常不能通过这些 API 调用，故这只是外部基线等量成本，不是托管自身 adapter 的报价。C 的裁判成本取决于每 rollout 是否程序判分；推荐程序真值，只有语义辅助才调用 API。D 的内部激活实验不能用普通黑盒 API 替代。

## 8. 成本风险、总计划与购买前校准

| 不确定来源 | 对预算的影响 | 实测/控制方法 |
|---|---|---|
| 上下文逐步增长、思考超长 | 输出与重复输入可数倍增长 | 用累计计费token而非初始prompt估算 |
| 并发、KV、张量并行 | 单卡峰值吞吐不等于实际每卡吞吐 | 记录集群总生成量÷总卡时 |
| 稀有 hacking、任务内相关 | 为同精度需更多独立任务 | Pilot 模拟功效；不要只增加解码重复 |
| 训练不收敛/优势全零 | 重试和调参可能主导成本 | 预留20–50%探索预算，上表f只覆盖一般开销，另行批准大规模调参 |
| 标注和CPU工具 | 不计入GPU吞吐仍有真实成本 | CPU秒/episode、人小时/轨迹独立报表 |
| 检查点及激活 | 可能超过模型推理日志数十倍 | 保存策略、压缩与生命周期预算 |

若自托管 GPU 单价为 g 美元/卡时，计算支出为 H×g；g 未报价，不提供虚构云成本。墙钟最低约 H/并发卡数，工具串行、排队和数据审计会延长，不可直接当工期。

**推荐决策预算**：先做 B Pilot 的960 episode：全部本地约20–100 GPU-hours，或一个 API 槽位约$112–187（含上述预留）＋剩余本地推理。Core B 全本地约400–2,200 GPU-hours。Full B 约4,000–47,000；若再加 Core C 与 Core D，算术规划区间约10,100–82,500 GPU-hours，存在共享评估可节省，也有长上下文可放大。四路线全部 Full 不作为默认计划。

是否值得投入应由 [08](08_Research_Decision.md)的科学门槛决定。完成 Pilot 前，不能把当前区间描述成保证能产出论文的报价。
